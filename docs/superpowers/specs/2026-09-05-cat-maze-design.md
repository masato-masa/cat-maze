## 1. コンセプト

盤面のタイルをスライドして迷路を作り替えながら、猫を歩かせてゴールへ導くパズルゲーム。

道は最初から繋がっていない。プレイヤーは「猫を歩かせる」と「盤面を作り替える」を交互に繰り返し、少しずつゴールへ近づく。

### 1.1 コアの体験（本作の存在理由）

> **1回のスライドで「道が繋がる」と同時に「猫が目的地側へ運ばれる」— この一石二鳥の手を発見する瞬間。**

猫が乗っているタイルをスライドすると、猫は足場ごと運ばれる。つまりスライドは道を作る手段であると同時に、**猫の移動手段**でもある。

この二重性から、プレイヤーは常に2つの問いを同時に抱える:

1. **どう道を繋ぐか**（空間パズル）
2. **自分はどこに立っておくか**（自分もまた動かされる駒である）

「足場そのものが動く」というこの性質が本作の固有性であり、すべてのステージ設計はこの瞬間を作り出すために存在する。

### 1.2 参考タイトルと差別化

| タイトル | 借りるもの | 本作との違い |
|---|---|---|
| ラビリンス（Das verrückte Labyrinth） | 道タイルを動かして経路を作る、駒が一緒に押される | 本作は押し出し循環ではなく「穴スライド」。可逆で詰みがなく、手数最適化パズルとして成立する |
| 15パズル / Klotski | 穴へ向けたスライド操作 | タイルに「道の接続」という意味があり、さらに盤上に動かす駒（猫）がいる |
| Pipe Mania / Pipe Roll | パイプ接続の判定 | パイプは置くのではなく「動かす」。かつ経路上を実際に歩く駒がいる |
| Rush Hour | 動かして道を空ける | 空けた道を「自分が」通る。かつ動かした物に乗って運ばれる |
| Cosmic Express / Snakebird | 手数最適化・少手数の濃い思考 | 難易度カーブとUndo設計の思想を借用 |

**差別化の一文**: ラビリンスの「足場が動く」快感を、15パズルの可逆性で詰みなく成立させ、少手数最適化パズルに仕立てたもの。

### 1.3 やらないこと（YAGNI）

- リアルタイム制・反射神経要素（v1では時間で状況が変わる要素を入れない）
- 手続き的ランダムステージ生成（パズルゲームの品質は手作りでしか担保できない）
- マルチプレイ、オンライン要素
- ステージエディタ（内部ツールとしては作るが、製品機能にはしない）

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 盤面 (Board) | W×H のグリッド。各セルはタイル1枚、または穴。 |
| タイル (Tile) | 盤面のマスを占める駒。道の接続情報を持つ。 |
| 穴 (Hole) | タイルが存在しないセル。盤面上に既定数（v1では1つ）存在する。猫は進入できない。 |
| 接続 (Connection) | タイルが持つ、北・東・南・西それぞれへの道の開閉を表す4bit値。 |
| 通行可能 (Passable) | 隣接する2セルの間を猫が移動できる状態。両タイルが互いの方向へ開いていること。 |
| 猫 (Cat) | プレイヤーが操作する駒。常にいずれかのタイルの上に乗っている。 |
| 歩行 (Walk) | 猫が隣接タイルへ移動すること。手数を消費しない。 |
| スライド (Slide) | 穴と同じ行または列のタイル群を穴の方向へ1マスずつずらす操作。1回につき1手を消費する。 |
| 手数 (Moves) | スライドの実行回数。本作におけるスコアの唯一の指標。 |
| 到達領域 (Reachable Set) | 現在の盤面で猫が歩行のみで到達できるセルの集合。 |

## 3. 盤面とタイル

### 3.1 盤面

- サイズは 4×4 〜 7×7。ステージごとに指定する。
- セルは「タイルが乗っている」か「穴」のいずれか。
- 穴の数は v1 では常に 1。ロードマップ上、複数穴ステージを後続ワールドで導入可能とするため、ロジックは最初から複数穴に対応させる。

### 3.2 タイルの接続

接続は4bitのビットマスクで表現する。

```
N = 1  (北)
E = 2  (東)
S = 4  (南)
W = 8  (西)
```

16通りすべてを有効な形状とする。

| 形状 | 値の例 | 個数 |
|---|---|---|
| 空き地（道なし） | 0 | 1 |
| 行き止まり | 1, 2, 4, 8 | 4 |
| 直線 | 5 (N+S), 10 (E+W) | 2 |
| カーブ | 3, 6, 12, 9 | 4 |
| T字 | 7, 14, 13, 11 | 4 |
| 十字 | 15 | 1 |

ステージごとに使用する形状を制限してよい（難易度調整の主要な手段のひとつ）。

**重要: タイルは回転しない。** スライドで位置が変わっても向きは保たれる。これはソルバーの状態空間を抑えるためと、プレイヤーが「あのタイルはあの形」と記憶して計画を立てられるようにするため。

### 3.3 タイルの種別

| 種別 | 説明 | スライド | 猫の進入 |
|---|---|---|---|
| `road` | 通常の道タイル | 可 | 接続に従う |
| `fixed` | 固定タイル（岩・切り株）。盤面に釘付け | **不可** | 接続に従う |
| `goal` | ゴールタイル（猫の家・餌皿） | 可 or 不可（ステージ指定） | 接続に従う |

ゴールタイルもスライドで動かせるようにするか固定するかは、ステージ設計者が選ぶ。**動くゴール**はそれ自体が強い設計素材になる（ゴールを猫の側へ運ぶ、という解法が生まれる）。

### 3.4 固定タイルの役割

固定タイルは本作の難易度設計における最重要素材である。理由は3つ:

1. **スライドを物理的に阻む** — 固定タイルを越えてタイルは動けないため、押せる範囲が制限される。
2. **盤面に骨格を与える** — すべてが動くと盤面が無定形になり、プレイヤーが計画を立てられない。固定タイルが「地図の目印」になる。
3. **探索空間を縮める** — 分岐が減るため、ソルバーによる最適解の検証が現実的な時間で終わる（§10参照）。

## 4. 操作とゲームループ

### 4.1 プレイヤーが取れる行動は2つだけ

| 行動 | 入力 | 手数 |
|---|---|---|
| 猫を歩かせる | 方向キー / 猫のスワイプ / 到達領域内のセルをタップ | **0手** |
| タイルをスライドする | タイルのタップ / タイルのドラッグ | **1手** |

### 4.2 なぜ歩行を0手にするか

これは本作の設計上もっとも重要な決定である。

- 歩行を有料にすると、プレイヤーは「歩くのがもったいない」という思考に支配され、盤面の構造ではなく歩数の節約に注意を奪われる。パズルの焦点がぼやける。
- 歩行を0手にすると、思考の対象が「盤面をどう変形するか」に一本化される。それでいて**猫の立ち位置は無意味にならない** — スライドの際に猫は足場ごと運ばれるため、「どこに立ってから押すか」が結果を変えるからである。
- 操作感としては、猫を自由にてくてく歩かせる気持ちよさがそのまま残る。

結果として、**アクション性（歩かせる楽しさ）とパズル性（手数最適化）が同じ操作体系の中で衝突せずに両立する。**

### 4.3 入力の曖昧さ解消

タップ操作が「歩行」と「スライド」のどちらを意味するかは、以下の優先順位で決定する。

1. 猫の**現在位置**をタップ → 何もしない
2. **穴**をタップ → 何もしない
3. **スライド可能なタイル**（穴と同じ行/列かつ、間に固定タイルが無い）をタップ → **スライド**
4. 上記以外で**到達領域内**のセルをタップ → その位置まで**歩行**（最短経路を自動でたどる）
5. それ以外 → 何もしない（「そこへは行けない」フィードバック）

方向キー / 猫のスワイプは常に**歩行**として解釈する。これにより、スライド可能なタイルの上に歩きたい場合でも方向キーで到達できる。

**設計意図**: タップは常にスライドを優先する。全 30 ステージの最適解を実測したところ、
**124 手のうち 40 手（32%）が「猫が乗っているタイル」または「猫が歩いて行けるタイル」を押す手**だった
（内訳: 猫自身のタイル 24 手、歩いて行けるタイル 16 手）。
歩行を優先すると、この 32% がタップだけでは実行できなくなる。したがってスライド優先は動かせない。

一方で「歩きたいのにスライドになってしまう」マスも実在する。実測では 154 局面の平均 0.84 マス、
最悪は W4-3 の 2 手目で 5 マス。この逃げ道として方向キーとスワイプを常時「歩行」に割り当てる。
両者が独立した操作であることは画面上に常時表示して伝える（凡例を出さないと発見できない）。

**スワイプとタップの競合**: スワイプのあとブラウザが click を発火することがあり、
そのまま通すと「歩く」と「スライド」が二重に起きる。スワイプを検出したら直後の click を 1 回だけ握りつぶす。
時間ではなく回数で打ち切ることで、その後の正当なタップを巻き込まない。

## 5. スライドの厳密な定義

### 5.1 前提

- 穴が `(hr, hc)` にある。
- 対象タイルが `(tr, tc)` にある。

### 5.2 スライド可能条件

対象タイルがスライド可能であるのは、以下をすべて満たすとき:

1. `tr == hr` または `tc == hc`（穴と同じ行または列にある）
2. 穴と対象タイルの間の区間（対象タイルを含み、穴を含まない）に `fixed` タイルが存在しない
   — 対象タイル自身が `fixed` の場合もこの条件で除外される

**穴が複数ある場合**（v2以降）: 対象タイルと同じ行/列にある穴のうち、対象タイルから**最も近い穴**を移動先とする。同距離の穴が両側にある場合はスライド不可（曖昧さを排除するため）。v1は穴が1つなのでこの規則は発火しない。

### 5.3 スライドの適用

穴と対象タイルの間の区間にあるタイル群が、**全体として穴の方向へ1マスずつずれる**。結果として穴は対象タイルがあった位置 `(tr, tc)` へ移動する。

疑似コード（水平方向の例）:

```
function slide(board, cat, targetPos):
    (hr, hc) = board.hole
    (tr, tc) = targetPos
    assert canSlide(board, targetPos)

    if tr == hr:                       # 水平スライド
        step = sign(hc - tc)           # タイルが動く向き（穴へ向かう向き）
        # 穴の隣から対象タイルまでを、穴側へ1つずつ詰める
        for c from (hc - step) to tc, stepping by (-step):
            board[hr][c] = board[hr][c - step]
            if cat == (hr, c - step):
                cat = (hr, c)          # ★ 猫は足場と一緒に運ばれる
        board.hole = (tr, tc)
    else:                              # 垂直スライドも同様
        ...

    moves += 1
    return (board, cat)
```

### 5.4 猫の運搬（本作の中核ルール）

- 猫が乗っているタイルがスライドの対象区間に含まれる場合、**猫はそのタイルに乗ったまま一緒に移動する**。
- 猫が穴の位置に来ることはない（猫はタイルの上にしか存在せず、穴は移動元ではなく移動先だから）。
- スライド後に猫の周囲の接続が変わり、猫が孤立することがある。これは失敗ではなく、パズルの一部である。

### 5.5 スライド1回 = 1手

区間内で何枚のタイルが動いても、1回のスライド操作は1手として数える。これによりテンポが良くなり、「盤面を大きく組み替える手」と「1マスだけ動かす手」が同じコストになるため、**ダイナミックな解法が報われる**。

### 5.6 可逆性

穴スライドはすべて可逆である（直前に押したタイルを押し返せば元に戻る）。したがって v1 のルール範囲では**詰み状態は存在しない**。これは以下を意味する:

- 「リトライ必須」のストレスがない
- プレイヤーは安心して試行錯誤できる
- ステージ設計者は「詰みチェック」を考えなくてよい

片道要素（消える床、使い切りの鍵など）を導入するとこの性質が壊れるため、v1 には持ち込まない（§8参照）。

## 6. 猫の歩行の厳密な定義

### 6.1 通行判定

セル `a` から隣接セル `b`（方向 `d`）へ猫が移動できるのは:

1. `a`, `b` がともに盤内である
2. `b` が穴でない（`a` は猫がいる時点で穴ではない）
3. `tile(a).conn` に方向 `d` のビットが立っている
4. `tile(b).conn` に方向 `opposite(d)` のビットが立っている

```
function passable(board, a, d):
    b = a + delta(d)
    if not inBounds(b): return false
    if board.isHole(a) or board.isHole(b): return false
    return (board.conn(a) & bit(d)) != 0
       and (board.conn(b) & bit(opposite(d))) != 0
```

**両側が開いている必要がある**（パイプ方式）。片側だけ開いている場合は通れない。これは視覚的に自明で、プレイヤーが誤解しない。

### 6.2 到達領域

猫の到達領域は、猫の現在位置からの通行可能グラフ上の連結成分。BFS/DFSで算出する。

UIは到達領域を常時ハイライトすべきである（本仕様の対象外だが、パズルの読みやすさに直結するため強く推奨）。

### 6.3 歩行は手数を消費しない

猫は到達領域内を自由に何度でも移動できる。歩行のみでは盤面状態は変化しない（v1では。踏むと変化するタイルを導入する場合はこの前提が変わる）。

## 7. 勝利条件とスコア

### 7.1 勝利条件

以下をすべて満たした瞬間にクリア:

1. 猫がゴールタイルの上にいる
2. ステージに収集物がある場合、すべて取得済み

### 7.2 スコア

**評価指標はスライド回数（手数）のみ。** 歩数・経過時間はスコアに含めない（表示はしてもよい）。

| 評価 | 条件 |
|---|---|
| ★☆☆ | クリアした |
| ★★☆ | `parMoves` 以内でクリア |
| ★★★ | `optimalMoves`（理論最小手数）ちょうどでクリア |

- `optimalMoves` はソルバーで算出した検証済みの値（§10）。
- `parMoves` は `optimalMoves + 2` 〜 `+4` を目安に、ステージの難易度に応じて設計者が設定する。

### 7.3 Undo とリトライ

- **Undo は無制限**。1手（1スライド）単位で巻き戻す。歩行は状態変化を伴わないためUndo対象外であり、Undoは常にスライド単位で巻き戻る（猫の位置もそのスライド直前の位置に戻る）。
- リトライ（初期状態に戻す）はいつでも可能。
- **Undo を使っても星評価にペナルティを与えない。** 最終的に何手でクリアしたかだけを見る。現代のパズルゲームの標準であり、思考実験のコストを下げることが良質な「読み」を促す。

実装上、Undo は「スライド適用前の完全な状態のスナップショット」をスタックに積むことで実現する。盤面は小さく状態も軽量なので、差分ではなくスナップショットで十分。

## 8. ギミック・ロードマップ

導入順は「1つのワールドで1つの新概念」を厳守する。

### 8.1 v1 に含めるもの

| # | ギミック | 内容 | 設計上の役割 |
|---|---|---|---|
| G1 | 道タイル | 接続16種 | 基本 |
| G2 | 穴 | スライドの自由度 かつ 通れない壁 | 基本 |
| G3 | 固定タイル | スライド不可の岩・切り株 | 盤面に骨格を与え、押せる方向を制限する |
| G4 | 魚（収集物） | 全部集めてからゴールへ | 一直線ではないルート設計を強制する。寄り道が「盤面をどう作り替えるか」の課題になる |
| G5 | 動くゴール | ゴールタイルもスライド対象 | 「猫が行く」から「ゴールを連れてくる」へ発想を転換させる |

**G5 は v1 の隠れた主役**である。ゴールが動くと気づいた瞬間、プレイヤーの盤面の見え方が一段変わる。

### 8.2 v2 以降の候補（本仕様では設計しない）

| ギミック | 内容 | 注意点 |
|---|---|---|
| 鍵と扉 | 色付きの扉タイル。対応する鍵を取ると通れる | 可逆性は保たれる |
| 複数の穴 | 穴が2つ以上 | ロジックは最初から対応済みにしておく |
| ワープ | 2つのタイルを繋ぐ土管 | 通行判定の拡張が必要 |
| 子猫 | 回収して連れて歩く / 2匹同時操作 | 状態空間が大きく増える。ソルバーの再検討が必要 |
| 氷タイル | 乗ると直進し続ける | 「歩行が0手」の前提と相性を検証すること |
| 犬（敵） | 時間軸で動く | **可逆性が壊れる。導入は慎重に。** 本作の魅力は落ち着いて考えられることであり、これを崩す価値があるか要検証 |

### 8.3 意図的に採用しないもの

- **制限時間** — 本作の快感は「盤面をじっと眺めて一石二鳥の手を見つける」ことにある。時間制限はこれを直接破壊する。タイムアタックは別モード（実績扱い）とし、本編には入れない。
- **ランダム生成ステージ** — 「一石二鳥の手」は設計者が意図して埋め込むものであり、ランダムでは生まれない。

## 9. ステージ設計方針

### 9.1 設計プロセス

1. **一石二鳥の手を先に決める** — このステージの「見せ場」となる1手を最初に紙の上で決める。「このスライドで道が繋がり、同時に猫が3マス運ばれる」という具体的な形。
2. **その手が最善になるように周囲を組む** — 素直に見える別解が同手数以下で存在しないよう、固定タイルと穴の初期位置で塞ぐ。
3. **ソルバーで検証する**（§10）— 最小手数を確定し、意図した解法が実際に最短であることを確認する。
4. **ミスリードを1つ用意する** — 一見良さそうだが2手余分にかかる経路。これがあると「気づいた」快感が生まれる。
5. **`parMoves` を設定する** — ミスリード経路の手数を目安にする。

### 9.2 難易度カーブの原則

- **1ワールド1概念。** 新概念は必ず「安全な練習ステージ」で単独導入し、その後に既習概念と掛け合わせる。
- **ワールド内の構成**: 導入（概念を単独で提示） → 練習（同じ概念を少しひねる） → 結合（既習概念と組み合わせる） → 反転（概念の前提を裏切る） → 総括（そのワールドの集大成）
- **チュートリアルテキストは書かない。** ステージの構造そのものが教える。最初のステージは「その操作しかできない」ように設計する（例: ステージ1では押せるタイルが1枚しかない）。

### 9.3 v1 のワールド構成

| ワールド | 主題 | ステージ数 | 盤面 | 最小手数の目安 |
|---|---|---|---|---|
| W1 うらにわ | 歩行とスライド、猫が運ばれることの発見 | 6 | 4×4 | 1〜4 |
| W2 いしだたみ | 固定タイル。押せる方向が限られる | 6 | 4×4 〜 5×5 | 3〜7 |
| W3 さかなつり | 収集物。ルートの順序が問題になる | 6 | 5×5 | 5〜10 |
| W4 うごくおうち | 動くゴール。発想の転換 | 6 | 5×5 | 6〜12 |
| W5 やねのうえ | 総合。全要素の組み合わせ | 8 | 5×5 〜 6×6 | 8〜16 |

合計 32ステージ。

### 9.4 W1 の詳細設計

**W1-1「はじめの一歩」** — 4×4。猫とゴールは直線で繋がっているが、間に1マスだけ道が途切れている。押せるタイルは1枚しかなく、それを押すと道が繋がる。最小1手。
- 教えること: タイルは押せる／押すと道が繋がる

**W1-2「のりもの」** — 4×4。猫の周囲は完全に閉じており、歩いてはどこにも行けない。しかし猫が乗っているタイルをスライドすると、猫ごとゴールの隣まで運ばれる。最小1手。
- 教えること: **猫は足場ごと運ばれる**（本作最重要ルール）
- 「歩けない」状況を強制することで、プレイヤーに発見させる

**W1-3「二回押す」** — 4×4。1手では届かず、2手必要。1手目で猫を運び、2手目で道を繋ぐ。最小2手。
- 教えること: 運搬と接続を組み合わせる

**W1-4「立ち位置」** — 4×4。同じスライドでも、猫がどこに立ってから押すかで結果が変わる。誤った立ち位置だと3手、正しい立ち位置なら2手。
- 教えること: **押す前にどこに立つかが重要**

**W1-5「穴のむこう」** — 4×4。穴を挟んで猫とゴールが対面している。穴は通れないので、穴を別の場所へ移動させる必要がある。最小3手。
- 教えること: 穴は壁でもある／穴の位置を能動的に動かす

**W1-6「うらにわ総括」** — 4×4。上記すべての組み合わせ。最小4手、`par` 6。

### 9.5 ステージデータ形式

以下は**フォーマットの説明のための例**であり、実際に W1-2 として成立する盤面ではない。実データは §9.4 の設計意図に沿って作成し、ソルバーで検証する。

```json
{
  "id": "EXAMPLE",
  "name": "フォーマット例",
  "width": 4,
  "height": 4,
  "layout": [
    ["EW", "ES", "WS", "X"],
    ["NS", "HOLE", "N", "NE"],
    ["FIXED:NS", "E", "EW", "W"],
    ["N", "NS", "GOAL:NW", "X"]
  ],
  "catStart": [1, 0],
  "optimalMoves": 1,
  "parMoves": 2,
  "hint": "歩けないときは、足場ごと動いてみよう"
}
```

- `layout` の各要素は接続を方角の文字列で表す（`X` = 空き地、`HOLE` = 穴）。
- `FIXED:` / `GOAL:` / `FISH:` は前置修飾子で、重ねて書ける。`FIXED:GOAL:NW` は動かないゴール、`FISH:EW` は魚の乗った直線路。
- 魚は `layout` の中に置く。ステージ定義に別の魚リストは持たない（配置情報が二重化するのを避けるため）。
- `optimalMoves` は**ソルバーが算出しビルド時に検証する**。手書きの値は信用しない。

## 10. ソルバーとステージ検証

### 10.1 なぜ必要か

★3の閾値 `optimalMoves` は、手作業では保証できない。設計者が5手だと思っているステージが実は3手で解ける、という事故はパズルゲームで頻発する。**ソルバーによる検証はステージデータの一部**として扱う。

### 10.2 探索状態

```
State = (タイル配置, 穴位置, 猫の到達領域の代表点, 取得済み収集物ビット)
```

**重要な状態圧縮**: 猫の正確な位置は状態に含めない。歩行が0手である以上、同じ盤面・同じ到達領域なら猫がどこに立っていても等価だからである。到達領域を正規化（含まれるセルのうち最小インデックス）して状態キーとする。

これにより状態数が最大で盤面セル数分の1に減る。

### 10.3 探索空間の見積もりと戦略

5×5盤面の配置は組み合わせ的に全探索不能。各手の分岐数は「穴と同じ行/列で押せるタイル数」で、最大 `(W-1) + (H-1)`（5×5 なら8）。

素朴なBFSは深さ12程度で破綻する。したがって:

**戦略: 逆生成 + 深さ制限付き反復深化（IDDFS）による下界証明**

1. **逆生成**: ゴール状態（猫がゴール上・収集物すべて取得済み）から、ランダムに N 回スライドを逆適用して初期状態を作る。これにより解が高々 N 手で存在することが保証される。
2. **下界証明**: 深さ `N-1` までの IDDFS を転置表付きで走らせ、解が存在しないことを確認する。存在すれば N を下げて再試行。
3. これにより `optimalMoves = N` が確定する。

深さ `N-1` までの探索は、`N ≤ 14` かつ固定タイルで分岐が抑えられていれば現実的な時間で終わる。**固定タイルは難易度設計だけでなく、検証の実行可能性のためにも必要**である。

### 10.4 手作りステージへの適用

逆生成で骨格を作った後、設計者が手で調整する（固定タイルの追加、ミスリード経路の埋め込み、見た目としての形の整え）。調整後に必ず再検証する。

- ソルバーは CLI ツールとして提供する: `npm run solve -- levels/W1-2.json`
- CI / ビルド時に全ステージを再検証し、`optimalMoves` の不一致をエラーにする。

### 10.5 ソルバーの副産物

- **ヒント機能**: 最適解の次の1手を提示できる。
- **難易度メトリクス**: 「最適解の分岐の狭さ」「ミスリード経路との手数差」を自動計測し、難易度カーブの検証に使う。
- **デッドロック検出**: 片道ギミックを v2 で導入する際に必要。

## 11. アーキテクチャ

### 11.1 レイヤ分割

```
src/
  core/            # 純粋なルールエンジン。UI・描画・入力を一切知らない
    types.ts       #   Tile, Board, GameState などの型定義
    board.ts       #   接続判定、到達領域の算出、盤面クエリ
    slide.ts       #   スライド可能判定、スライド適用（猫の運搬を含む）
    rules.ts       #   勝利判定、収集物、星評価
    game.ts        #   GameState と操作の適用、Undo スタック
  solver/          # 探索。core にのみ依存する
    search.ts      #   IDDFS + 転置表
    generate.ts    #   逆生成
    cli.ts         #   ステージ検証 CLI
  levels/          # ステージ JSON
  ui/              # 描画・入力。core を呼ぶだけ。（本仕様の対象外）
```

### 11.2 設計上の制約

- **`core/` は完全に純粋関数で構成する。** 乱数・時刻・DOM・グローバル状態に依存しない。すべての関数は `(state, input) => newState` の形を取る。
- **状態はイミュータブル。** スライドは新しい状態を返す。これにより Undo がスナップショットの積み上げだけで実装でき、ソルバーが同じコードを再利用できる。
- **`solver/` は `core/` のルール実装をそのまま使う。** ソルバー用にルールを再実装してはならない（実装が乖離すると検証が無意味になる）。
- **`ui/` から `core/` の内部状態を直接書き換えない。**

### 11.3 主要な型（草案）

以下は Q1（§13）を「TypeScript + Web」と解決した前提で記述している。別プラットフォームを選ぶ場合、レイヤ分割（§11.1）と制約（§11.2）はそのまま適用し、型定義のみ読み替える。

```ts
type Dir = 0 | 1 | 2 | 3;              // N, E, S, W
type Conn = number;                     // 0..15 のビットマスク
type Pos = { r: number; c: number };

type TileKind = 'road' | 'fixed' | 'goal';

type Tile = {
  id: number;                           // 不変。UIのアニメーション追跡に使う
  conn: Conn;
  kind: TileKind;
  fish: boolean;
};

type Board = {
  width: number;
  height: number;
  cells: (Tile | null)[];               // null = 穴。これが穴位置の唯一の情報源
  // 穴の位置は cells から導出する（holes(board): Pos[]）。
  // 冗長なフィールドを持たせると同期ずれの温床になるため保持しない。
  // §5 の疑似コード中の board.hole は、この導出関数の結果を指す。
};

type GameState = {
  board: Board;
  cat: Pos;
  moves: number;                        // スライド回数
  fishTaken: number;
  fishTotal: number;
  cleared: boolean;
};
```

`Tile.id` を不変にしておくことで、UI 層がスライド時に「どのタイルがどこへ動いたか」を追跡してアニメーションできる。ロジック上は不要だが、後で追加すると破壊的変更になるため最初から入れる。

### 11.4 開発方針

- **TDD で `core/` を作る。** ルールエンジンは純粋関数の集合であり、テストが極めて書きやすい。最初に書くべきテストの例:
  - 両側が開いた隣接タイル間は通行可能、片側だけなら不可
  - 穴には進入できない
  - 固定タイルを越えてスライドできない
  - 猫が乗ったタイルをスライドすると猫の座標が追従する
  - スライドは可逆（押して押し返すと元の状態に戻る）
  - 収集物を取らずにゴールに乗ってもクリアにならない
- ソルバーは `core/` が完成してから着手する。
- UI は最後。**まず CLI で遊べる状態を作る**（盤面をテキスト描画し、キー入力で操作できる）。これによりルールの手触りを UI 実装前に検証できる。

## 14. 設計判断のまとめ

本仕様でもっとも重要な3つの決定と、その理由:

1. **穴スライド方式を採用した** — 穴が「スライドの自由度」と「猫が通れない壁」を兼ねる。完全可逆で詰みがなく、手数最適化パズルとして成立する。
2. **歩行を0手、スライドを1手とした** — 猫を歩かせる操作感を保ちながら、思考の対象を盤面変形に一本化した。猫の立ち位置はスライド時の運搬を通じて意味を持ち続ける。
3. **ステージは手作りし、ソルバーで検証する** — 「一石二鳥の手」は設計者が意図して埋め込むものであり、ランダム生成では生まれない。しかし最小手数は人力では保証できないため、ソルバーによる検証をステージデータの一部とする。
